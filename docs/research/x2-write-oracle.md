# X2 — write 정책 오라클 상한 (미완 — 유료 재실행 대기)

2026-08-19. 상태: **$0 절반만 완료.** 아래 수치는 전부 기존 커밋 아티팩트의 재배열이고
(`scripts/repro/x2_oracle_prep.py`, 전 arm docs/18 앵커 대조 후에만 기록), 프록시 store에 대한
retrieval+answer+judge 재실행(arm당 $0.30–1.37 견적, 합계 ~$4.25)은 **승인 전이라 실행하지
않았다**. 재실행이 채울 자리는 표에 빈 칸으로 남겨 둔다.

질문(계획 §X2): 학습된 write 정책의 이득 상한은 얼마인가. Mem0의 79% NOOP는 좋은 판단이었나.

## 정의 — 프록시와 괄호

"기여" = 채점된 1,540문항 중 j=True 문항의 서빙 컨텍스트(`retrieval.retrieved`)에 1회 이상
등장. **프록시 오라클 store = 기여 항목만 보존.** 진짜 오라클 J*(부분집합 선택 최적)는
반사실이라 직접 측정 불가 — 다음 쌍으로 괄호를 친다(설계 확정은 계획 §X2의 2026-08-19 추기):

- **하한**: 프록시 store 재실행 J. 순수 dense read(Nemori·Mem0)에서는 정답 문항의 서빙 top-k가
  필터링 후 그대로 보존되므로(정답 컨텍스트 항목은 정의상 전부 기여, dense 점수는 pool 독립)
  실측 J 근방 이상이 기대되고, pool 의존 read(Zep의 BM25/BFS/reranker 융합, A-Mem의 링크
  확장)에서는 그 보장이 없다.
- **상한**: write-coverage ceiling — 증거 turn 유래 항목이 store에 전무한 문항의 비율로 계산.
  `source_episode_ids` 계보가 필요하며(4/5 arm 보유, **Mem0 부재** — 아래), episodic id→세션:턴
  좌표 복원(ops 순서 × locomo10.json 조인)이 남아 유료 라운드의 분석 단계와 함께 수행 예정.

## 이 표가 이미 말하는 것, 그리고 말할 수 없는 것

1. **Nemori에는 빼기 오라클의 여지가 거의 없다.** arm B는 store의 95.6%가 정답 컨텍스트에
   실제로 올랐다 — 프록시 store가 원본과 거의 같으므로, 유료 재실행은 실측 J 근방을 돌려줄
   것이 거의 확실하고(순수 dense — 보존 논거 성립), 그 자체가 발견이다: **이 arm의 write
   정책이 남긴 "학습으로 지울 살"이 없다.**
2. **Mem0·Zep은 store의 절반이 정답에 한 번도 기여하지 않았다.** 다만 이 삭제율은 성능
   조건부다: J가 낮을수록 정답 컨텍스트 슬롯이 적어(Mem0 490문항×30 = 14,700 슬롯) 기여
   기회 자체가 줄어드는 방향의 교락이 있다. "절반이 죽은 무게"와 "절반에게 기회가 없었다"를
   이 표만으로는 가르지 못한다 — 그걸 가르는 것이 유료 재실행이다.
3. **빼기 오라클은 Mem0의 주 결손을 원리적으로 못 닫는다.** docs/18의 분해로 Mem0 결손
   35.8pt 중 ~26pt는 커버리지(기권 55.6%)다. 항목을 지우는 오라클은 커버리지를 **만들** 수
   없다 — 재실행이 닫을 수 있는 것은 잘못-답변의 정돈(정확도 성분 ≤10pt)뿐이다. 커버리지
   쪽 상한은 계보 기반 ceiling(위)의 몫이고, Mem0은 계보 부재로 그 계산이 막혀 있다.
   **사전 등록 격의 기대**: Mem0 재실행 J의 상승 폭은 한 자릿수 pt를 넘지 못한다.
4. **Mem0의 79% NOOP는 항목 수준에서는 나쁜 판단이 아니었다.** NOOP(기존 항목 재확인)를
   1회 이상 받은 최종 store 항목의 기여율 **53.2%** vs 한 번도 재확인되지 않은 항목 **41.0%**
   (store 전체 50.5%) — 정책이 "이미 있다"고 반복 판정한 항목일수록 실제로 쓸모가 있었다.
   자기모순은 소수: NOOP 대상이었다가 나중에 DELETE된 항목 174개, ADD 후 DELETE 227개,
   상류가 세지 않는 discard는 hallucinated_id 184건(10 conv 합, per-conv ingest 요약 `drops`).
   NOOP 최다 수신 항목은 68회. — 즉 X2의 원질문 후반부("79% NOOP는 좋은 판단이었나")의
   $0 답: **재확인 판정의 방향은 유용성과 양의 상관, 문제는 판정이 아니라 남긴 단위의 크기와
   커버리지다.**

## 유료 재실행 계획 (승인 대기 — 견적은 각 arm의 실측 eval 비용)

prep.json의 `paid_step`에 기계가 읽을 형태로 동일 내용이 있다. 공통: keep_ids로 store 재구성
(임베딩은 커밋 스냅샷의 `embedding_text` 재사용 — 저장 항목 임베딩 지출 0), 해당 arm의
headline read path 그대로, 1,986문항 answer + 1,540 judge.

| arm | store | 예상 콜 (generate/judge/read-side) | 견적 |
|---|---|---|---|
| Nemori arm A | `keep_ids/nemori_a.json` (2,380) | 1,986 / 1,540 / 0 | $1.37 |
| Nemori arm B | `keep_ids/nemori_b.json` (2,418) | 1,986 / 1,540 / 0 | $1.12 |
| A-Mem | `keep_ids/amem.json` (4,378) | 1,986 / 1,540 / 1,986 (키워드 재작성은 계보) | $1.09 |
| Zep cross_encoder | `keep_ids/zep_cross_encoder.json` (6,263) | 1,986 / 1,540 / 0 (+GPU reranker, eval 벽시계 ~8,528s) | $0.38 |

합계 견적 **~$4.25** (계획 앵커 "arm당 $0.3–1.4" 내). 계획 §5 결정 ①에 따라 Phase 2 캡과
별도 캡으로 승인받을 것. 재실행 후 이 문서의 "재실행 J" 열과 §3의 판정(특히 2·3번의 교락
해소), 계보 기반 ceiling(4/5 arm)을 채운다.
