# v1 제품 완료 기준과 현재 상태

2026-09-09. **v1의 제품 효용까지 검증된 것은 아니다.** 구현·운영 계약과 효과 검증을 분리한다.
기존 docs/23의 “새 세션에 runbook 5줄 주입”은 도그푸딩 이정표이며 제품 출시 판정이 아니다.

## 사용자가 기대하는 결과

다음 세션에서 이전 작업의 제약·결정·실패와 해결 절차를 다시 설명하지 않아도 된다.
필요한 기억을 근거와 함께 확인하고, 잘못되었거나 낡은 기억은 교정·제외할 수 있어야 한다.
저장·증류·검색이 실패해도 기록과 실패 이유를 확인하고 복구할 수 있어야 한다.

원문 보존 → 경험 정리 → 검색·주입 → 다음 작업 활용 → 교정·폐기 → 운영·복구가 하나의 제품 흐름이다.
자동 주입은 daemon 검색 또는 BM25 fallback이고, MCP `research_memory` 원문 탐색기는 별도 경로다.
탐색기의 기존 벤치마크 결과를 자동 주입이나 실제 코딩 생산성의 증거로 옮겨 해석하지 않는다.

## 전체 상태

| 영역 | 구현·검증한 계약 | 남아 있는 한계 |
|---|---|---|
| 원문·작업 복구 | 훅 namespace 일치, HTTP 성공 전 디스크 작업 접수, 실패 보존, 미개방 namespace 발견, 재시작·동시 소비 테스트 | 작업은 원문 경로를 참조하며 원문 파일 자체의 스냅샷은 아님. 외부 호출 exactly-once 아님 |
| 경험 정리 | 원문 버전별 상태, 진행 중 중복 방지, 완료/생략/부분/실패 구분, 실패 재시도, 부분 결과에서 이전 기억 보존 | 여러 세션에 걸친 의미적 중복·상충 해결과 장기 품질은 미검증 |
| 기억 품질 | 입력 범위·인용 상태·문자 잘림·모델 판단 출처 표시, 정확히 같은 출력 중복 제거, 잘못된 구조의 출력 관측 | 정확한 인용이 내용의 참·유용성을 증명하지 않음. 일반론/잘못된 결론의 의미적 판별은 미완료 |
| 검색·주입 | 역할·프로젝트·namespace 필터, 전역 top-k, daemon/fallback/SessionStart의 사용자 제어 | 후보 상한 4096, cwd 미상 허용, 실제 관련성·장문 누적 열화 평가 필요 |
| 사용자 교정 | CLI/MCP inspect·disable·correct·restore, 원본/변경 로그, 원문·runbook 제어, harmful 자동 주입 제외 | 연관 기억 전체에 자동 교정 전파하지 않음. 오프라인 교정 후 벡터 재생성은 대기 상태로 표시 |
| 운영 | 상태·실패 사유·대기열 수, 실행 소스/설정 지문과 로컬 비교, 외부 호출 없는 전체 제품 smoke, timeout/소유 프로세스 정리 | 실제 호스트 업데이트 후 설치 유지 및 장기 운영 안정성은 별도 현장 검증 필요 |
| 효과 평가 준비 | 무기억/원문/runbook 비교, 작은 코딩 사례 4개와 판정 코드, 입력·설정·소스 hash 고정, 결과 스키마, **실행기 `run`(2026-09-10, 스텁 에이전트로 끝까지 검증)** | 실제 에이전트 12건 실행과 사용자 생산성 측정은 아직 실행하지 않음(유료, 사용자 착수 필요) |

수치 성능 기준은 아직 사용자와 확정하지 않았다. 테스트 통과나 주입 성공 횟수를 효용 지표로 대신하지 않는다.

## 이번 후속 구현이 바꾸는 실제 동작

1. `preserve` 후 동일 원문을 `distill`해도 경험 정리가 생략되지 않는다.
   원문 episode 존재와 증류 상태를 분리하고, 원문 내용이 바뀌면 다른 revision으로 취급한다.
2. `queued: true` 전에 디스크에 작업을 기록한다. 재시작 후 열린 적 없는 namespace의 큐도 찾는다.
   성공 행만 제거하고 실패 행은 `.processing`, 해석 불가·파일 없음은 사유와 함께 `.bad`에 남긴다.
3. 모델 미설정·응답 손실을 성공으로 기록하지 않는다. 정상 응답에 남길 신호가 없으면 `skipped`,
   일부 결과만 얻으면 `partial`, 실패하면 `failed`로 남긴다. 부분 결과는 자동으로 전체 재과금하지 않는다.
4. runbook에 모델이 본 단계와 인용 단계의 비율을 따로 남긴다. 한 단계 내부가 잘린 경우도 표시한다.
   모델이 `success`라고 썼다고 독립 검증된 사실로 표시하지 않는다.
5. 잘못된 기억을 비활성화하거나 교정할 수 있고, 자동 주입 세 경로에 동일하게 적용한다.
   harmful은 기록에만 머물지 않고 주입 제외에 반영한다. 복원 후 새 harmful 피드백은 다시 제외한다.
6. 현재 CLI와 실행 중 daemon의 저장소·설정·소스 지문을 비교한다. 살아 있지만 오래된 실행을 건강하다고 간주하지 않는다.
7. 코딩 평가에 사용할 실제 시작 코드와 판정 스크립트를 고정한다. 준비 CLI는 모델이나 에이전트를 실행하지 않는다.

## 운영 명령과 평가 준비

[운영·교정 설명](29-v1-operations-and-controls.md)에서 상태 확인, 교정, 복원, 증류 결과와 대기열 의미를 설명한다.
[코딩 평가 준비](28-coding-memory-evaluation.md)는 네 개 과제와 비교 조건, prepare/verify 명령을 설명한다.

```bash
uv run --no-sync python -m agmem.bench.coding_eval verify /tmp/coding-eval-manifest.json
```

## 보장의 경계

- POSIX 파일 잠금과 fsync를 사용한다. 프로세스 중단 후 at-least-once 복구이며 전원 장애·외부 제공자 과금까지의 분산 트랜잭션 보장은 아니다.
- 원문 파일이 사라지면 path job만으로 원문을 재구성할 수 없다. 누락은 조용히 성공 처리하지 않고 검사 가능한 상태로 남긴다.
- 자동 주입 비활성화는 물리적 삭제가 아니다. 수동 조사·검토 경로에서 원본을 확인할 수 있다.
- 새 품질 상태가 없는 과거 기억은 미상이다. 과거 live runbook을 자동으로 유료 재증류하지 않으며 강제 복구는 명시적으로 수행한다.
- 품질 표시는 참/거짓 판별기가 아니다. 인용 누락은 표시하되 기존 세션 전체 출처 fallback을 유지한다.
- 교정의 원본과 감사 로그를 보존한다. 관련 원문·다른 runbook을 자동으로 일괄 수정하지 않는다.
- 기존 LME-V2 비용 ledger/budget은 오프라인 회계다. 운영 증류·탐색에 대한 실제 금액 기준 강제 차단과 같지 않다.
- 실제 유료 측정, 운영 daemon 교체, 사용자 설치 설정 변경은 이번 실행에 포함하지 않는다.

## 완료 판정

최종 로컬 검증: 관련 통합 테스트 219개 통과, 마지막 예외 타입·CLI 분기 정리 후 관련 테스트 17개 추가 통과.
`smoke_product_stack.py --hermetic --daemon`은 임시 daemon과 로컬 모델 대역으로
캡처·MCP·보존·증류·다음 세션 회상·doctor를 실행해 `VERDICT: ok`를 반환했다.
코딩 평가 prepare/verify는 `valid: true`였으며 성과 결과는 채우지 않았다.
새 모듈 21개 타입 오류 0개, 변경 범위 Ruff와 새 모듈 정적 규칙 검사를 통과했다.
기존 핵심 파일(memory/server/pipeline)에 남아 있던 엄격한 타입 오류 10개는 2026-09-10에 정리했다
(전부 `memory.py`의 인자 없는 `dict` 주석이었고, basedpyright 기준 세 파일 오류 0개).
경고 500여 건은 그대로이며, 저장소 전체 정적 검사 완료를 주장하지 않는다.

이번 작업의 완료는 위 구현 계약을 로컬 CLI·HTTP·저장소·회귀 테스트로 검증했다는 뜻이다.
v1의 실제 효용·장기 안정성까지 검증됐다는 뜻은 아니다. 다음 제품 판정은 준비한 과제를 실제 에이전트로 수행한 결과와
사용자 도그푸딩에서의 성공·재설명·오류·지연·비용 증거를 근거로 내려야 한다.
